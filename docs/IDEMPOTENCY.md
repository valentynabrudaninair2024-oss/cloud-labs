# Ідемпотентність запису

**Покращує:** надійність — повтор запиту з тим самим ключем дає один запис і ту саму відповідь замість дубліката або помилки.  
**Коштує:** два звернення до Redis на кожен запис з ключем і зберігання відповіді 24 години.  
**Відкинули:** захист лише унікальним полем (повтор отримає `409`, і клієнт не знатиме, що перший запит спрацював), відмову `503` при недоступному Redis (запис важливіший за захист від рідкісного повтору).

## Навіщо

Читач натиснув «Створити», запит дійшов, філію створено, а відповідь загубилася в мережі. Клієнт не знає результату і повторює запит. Без захисту — помилка «телефон уже існує» або, для сутностей без унікальних полів, дублікат.

Клієнт додає заголовок `Idempotency-Key` з випадковим UUID і використовує той самий ключ для всіх повторів однієї дії.

## Як зроблено

Декоратор `@idempotent` (`app/library/idempotency.py`) на `POST /libraries` і `POST /libraries/async`:

| Ситуація | Відповідь |
|---|---|
| Немає ключа | Запит виконується як звичайно |
| Перший запит з ключем | `SET NX` блокування на 60 с → виконання → відповідь зберігається на 24 год |
| Повтор, перший ще виконується | `409` і `Retry-After: 1` |
| Повтор з тим самим тілом | Збережена відповідь, заголовок `Idempotent-Replayed: true` |
| Той самий ключ, інше тіло | `422` |
| Відповідь 5xx або виняток | Ключ видаляється, клієнт може повторити |
| Redis недоступний | Запит виконується без захисту, у лог — попередження |

Відбиток запиту — SHA-256 від методу, шляху і тіла. Ключ у Redis — `idem:<шлях>:<ключ>`, тож той самий ключ на різних ендпоінтах не конфліктує.

## Два рівні захисту для черги

1. `Idempotency-Key` на `POST /libraries/async` — повтор клієнта отримає той самий `job_id`, і друге повідомлення в чергу не потрапить.
2. Таблиця `processed_jobs` в обробнику — якщо сама черга доставить повідомлення двічі (див. [QUEUE.md](QUEUE.md)).

Разом: одне натискання кнопки — рівно одна філія.

## Тести

`tests/test_idempotency.py`, запускаються проти локального `docker compose`:

```bash
python -m pytest -v tests/test_idempotency.py
```

| Тест | Що перевіряє |
|---|---|
| `test_same_key_creates_one_library_and_replays_response` | Два однакові запити з ключем → один `INSERT` (лічильник `Com_insert` з `/stats`), однакові відповіді, `Idempotent-Replayed` |
| `test_without_key_repeat_is_executed_again` | Без ключа повтор виконується і отримує `409` |
| `test_same_key_with_other_body_is_rejected` | Ключ з іншим тілом → `422` |
| `test_async_same_key_enqueues_once` | Повтор `async` з ключем → той самий `job_id`, рівно один запис |
| `test_worker_skips_redelivered_message` | Повторне повідомлення в черзі не створює другої філії |

Ті самі тести запускаються в GitHub Actions перед кожним деплоєм.
