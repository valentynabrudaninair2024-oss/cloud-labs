# Ідемпотентність запису

**Покращує:** надійність — два однакові POST з одним ключем дають одну філію і однакову відповідь замість дубліката чи помилки.  
**Коштує:** звернення до Redis на кожен запис з ключем і зберігання відповіді 24 години.  
**Відкинули:** захист лише унікальним телефоном (повтор отримує помилку), відмову 503 при недоступному Redis.

## Навіщо це

Буває, що клієнт надіслав запит на створення філії, а відповідь не дійшла, наприклад, зник інтернет. Клієнт не знає, чи філію створено, і надсилає запит ще раз. Без захисту другий запит отримає помилку «такий телефон уже є» або, якщо унікального поля немає, створить дублікат. Хоча насправді перший запит спрацював.

Щоб цього не було, клієнт додає до запиту заголовок `Idempotency-Key` з унікальним ключем. Якщо прийде повтор з тим самим ключем, сервер нічого не створює вдруге, а повертає ту саму відповідь, що й першого разу.

## Як зроблено

Відповідь на запит з ключем зберігається в Redis на 24 години. Поки перший запит ще виконується, повтор отримує відповідь «зачекайте» (409). Якщо той самий ключ прийде з іншими даними, сервер поверне помилку 422. Відповіді з помилкою сервера не зберігаються, щоб клієнт міг спробувати ще раз. Якщо Redis недоступний, запит просто виконується без захисту — записати важливіше, ніж захиститися від рідкісного повтору. Код у `app/library/idempotency.py`.

## Тест

Тести лежать у `tests/test_idempotency.py` і запускаються проти локального `docker compose`:

```bash
python -m pytest -v tests/
```

Головний тест надсилає два однакові запити з одним ключем. Він перевіряє, що в базі з'явився лише один запис, а обидві відповіді однакові. Інші тести перевіряють, що без ключа повтор виконується ще раз, що той самий ключ з іншими даними відхиляється і що повторне повідомлення з черги не створює другої філії. Разом з тестами самого API їх 12, і всі проходять — і локально, і в GitHub Actions, де вони запускаються перед кожним деплоєм.

## Як це пов'язано з чергою

Захист від дублікатів працює у двох місцях. Ключ на запиті до черги захищає від повтору з боку клієнта: повторний запит отримає той самий номер задачі, і друге повідомлення в чергу не потрапить. А таблиця виконаних задач в обробнику захищає від того, що черга сама доставить повідомлення двічі. Разом вони гарантують, що одне натискання кнопки створить рівно одну філію.
